# Roadmap: MusicGenerator

## Overview

MusicGenerator ships in four phases: stand up the infrastructure and validate the ACE-Step API end-to-end, build the full generation API with all input options, deliver in-browser playback and audio downloads, then close with UX polish and a landing page. Every phase delivers a coherent, testable capability that unblocks the next. The result is a working web app where anyone can generate a personalized song in seconds.

## Phases

**Phase Numbering:**
- Integer phases (1, 2, 3): Planned milestone work
- Decimal phases (2.1, 2.2): Urgent insertions (marked with INSERTED)

Decimal phases appear between their surrounding integers in numeric order.

- [ ] **Phase 3: Playback and Download** - In-browser waveform player and MP3/WAV download

## Phase Details

### Phase 1: Infrastructure Foundation
**Goal**: The underlying stack is running and verified — database is migrated, ACE-Step API is validated, and a song can be generated by hitting the API directly with no UI. No auth in v1.
**Depends on**: Nothing (first phase)
**Requirements**: INFRA-01, INFRA-02, INFRA-03
**Success Criteria** (what must be TRUE):
  1. A direct API call to the RunPod endpoint returns a completed audio file (no UI required)
  2. ACE-Step worker restart policy is active and the memory leak does not accumulate across multiple test generations
  3. The Next.js app boots and serves API routes
  4. Supabase schema is migrated (generations, outputs tables exist and Drizzle ORM can query them)
  5. A generation error returns a clear error response with a retry signal rather than a silent hang
**Plans:** 2/3 plans executed

### Phase 2: Generation API
**Goal**: Users can submit any combination of text prompt, custom lyrics, genre tags, duration, and instrumental mode and receive two song variants back through the full BFF stack.
**Depends on**: Phase 1
**Requirements**: GEN-01, GEN-02, GEN-03, GEN-04, GEN-05, GEN-06
**Success Criteria** (what must be TRUE):
  1. User types a plain-text vibe description and receives two distinct song variants
  2. User enters custom lyrics with [Verse]/[Chorus] tags and the generated song reflects the structure
  3. User selects a duration preset (Short, Standard, Full) and the output audio matches the chosen length
  4. User enables instrumental mode and the output contains no vocals
  5. Frontend polls /api/status/:jobId every 2.5 seconds — the Vercel function never times out waiting for RunPod

### Phase 3: Playback and Download
**Goal**: Users can listen to their generated songs in-browser with a waveform visualization and download them as MP3 or WAV.
**Depends on**: Phase 2
**Requirements**: PLAY-01, PLAY-02, PLAY-03
**Success Criteria** (what must be TRUE):
  1. User can play, pause, and seek within a generated song using a waveform visualization (not a plain audio element)
  2. User can download a generated song as an MP3 file that plays in standard media players
  3. User can download a generated song as a WAV file
  4. Both song variants from a generation are independently playable and downloadable without navigating away

### Phase 4: UX Polish
**Goal**: The generation experience is smooth and clear — users know what mode they are in, see meaningful feedback while waiting, and arrive at the app through a landing page that sets expectations.
**Depends on**: Phase 3
**Requirements**: UX-01, UX-02, UX-03
**Success Criteria** (what must be TRUE):
  1. During generation, an animated loading state with named stage progression (e.g., "Initializing" -> "Generating" -> "Finalizing") replaces the input form — no plain spinner
  2. User can switch between Simple mode (text prompt) and Custom mode (lyrics + style tags) via a visible toggle with each mode displaying the appropriate input fields
  3. A landing page exists with example generations and a call-to-action that leads directly to the generation UI
